Relay's Rust diagnostic foundation provides component-scoped recording and
read-only snapshots. Serializable contracts live in `nemo-relay-types`;
registration, retention, and queries live in `nemo_relay::diagnostics`.
Recording requires no logger, plugin activation, Tokio runtime, or HTTP listener.

## Startup Enablement

Diagnostics is compiled in and **disabled by default**. The runtime owner selects
`DiagnosticsSettings.enabled` when creating a context. This is a startup runtime
setting, with no Cargo feature or live enable/disable switch.

Pass the same context to producers and readers. Disabled recorders preserve the
producer interface, skip lazy observation factories, and allocate no backend
pools. Reading a disabled context returns `DiagnosticError::Disabled`.

For process-wide convenience constructors, call
`Diagnostics::install_process_default` before creating logging or plugin
components. The first `Diagnostics::process_default()` lookup otherwise installs
a disabled context; existing handles are never implicitly upgraded.

For an explicitly owned plugin host, use
`nemo_relay::plugin::initialize_with_diagnostics(config, additional_plugins_toml, &diagnostics)`.
The host passes that same context through configuration resolution and common
component activation. The existing `initialize` convenience API selects the
process default. Standalone validation and discovery do not consume that default.

## Recording and Reading

Register the component's expected codes before recording. Each observation
supplies a positive `NonZeroU64` occurrence delta, rather than a previously
accumulated total. Zero cannot be authored through the recording constructors;
wire snapshots retain their lossless numeric-string representation.
This example records typed evidence for a sink without configuring logging.
Supply the deployed Relay version in the source identity.

```rust
use std::num::NonZeroU64;
use nemo_relay::diagnostics::{
    BuiltinDiagnosticCode, Classification, ComponentRegistration, DiagnosticQuery,
    Diagnostics, DiagnosticsSettings, FailureClass, FailureCode, LoggingFailureCode,
    Observation, SourceIdentity, SuccessCode,
};

let diagnostics = Diagnostics::from_settings(
    SourceIdentity {
        instance_id: uuid::Uuid::now_v7(),
        process_id: Some(std::process::id()),
        process_role: "embedded".into(),
        relay_version: "0.11.0".into(),
    },
    DiagnosticsSettings { enabled: true, ..Default::default() },
)?;
let failure_code = FailureCode::Logging(LoggingFailureCode::SinkWriteFailed);
let success_code = SuccessCode::SinkInitialized;
let codes = [
    BuiltinDiagnosticCode::Failure(failure_code),
    BuiltinDiagnosticCode::Success(success_code),
];
let component = diagnostics.register_component(ComponentRegistration::new(
    "example.logging_sink", &codes,
))?;
component.record_lazy(|| Observation::new(
    Classification::failure(failure_code, FailureClass::Io)
        .expect("supported sink failure class"),
    "The sink write failed",
    NonZeroU64::new(2).expect("positive diagnostic occurrence count"),
))?;
component.record_lazy(|| Observation::new(
    Classification::success(success_code),
    "The sink initialized",
    NonZeroU64::MIN,
))?;

let page = diagnostics.snapshot(&DiagnosticQuery::default())?;
let encoded: &[u8] = page.as_bytes();
assert!(!encoded.is_empty());
let snapshot = page.to_snapshot()?;
assert_eq!(snapshot.components.len(), 1);
assert_eq!(snapshot.lifetime.totals.failures_total.value.get(), 2);
drop(page); // Return the leased query workspace.
```

`SnapshotLease::as_bytes()` borrows the canonical JSON page. The lease occupies a
reserved query workspace until dropped. `to_snapshot()` decodes a separate
caller-owned value; those allocations are outside the service's memory budget.
The query is borrowed during capture; the returned lease owns its copied page
and does not borrow the query. Reuse one `DiagnosticQuery` for polling and update
its continuation between pages without cloning selector strings.
Reads add no occurrences and reset no counters. Later success leaves earlier
failure counts intact.

## Shared Payload Models

Producers and decoded events use the same public `Classification`,
`PluginObservationContext`, and `DiagnosticCorrelation` payloads. Typed catalogue
constructors supply canonical names without allocating strings. The payloads use
borrowed-or-owned strings: decoded snapshots own their values and preserve names
that a reader does not yet recognize. `Classification` has private fields and
read-only `code()` and `failure_class()` accessors. Typed constructors validate
built-in pairs; `from_opaque_names()` explicitly preserves opaque wire or admitted
extension names. Opaque construction and Serde decoding do not authorize recording:
core validates the catalogue, ownership, and generation at admission. `into_names()`
transfers the strings without cloning when an adapter needs to reuse owned buffers.

`DiagnosticCorrelation<'a>` also lets producers borrow dynamic request/session
IDs for the duration of recording. Decoded events use owned
`DiagnosticCorrelation<'static>` values; the lifetime does not require received
IDs to be static. Deserialization owns incoming strings rather than borrowing
from the input buffer.

The public payloads and `Observation` are `Clone`, rather than `Copy`. Core
validates recording input before updating counters and encodes accepted names
into its private fixed-size storage. A readable unfamiliar code, cause, or plugin
context does not authorize recording it. Built-in classification must match the
catalogue, and extensions require their admitted handles with ownership and
generation checks. Known plugin context is validated independently of counter
identity. Construct context names with the corresponding `PluginExecution` or
`PluginPhase` enum. Their distinct wrappers reject swapped enum values in Rust;
`from_opaque_name()` and decoding preserve future strings. Unknown names remain
readable but are rejected by core recording until supported.

`Observation` remains the recording input; `DiagnosticEvent` contains accepted
evidence with runtime-assigned identity, sequence, and timestamps. Lazy detail
formatting and retained detail also keep their separate input/result roles.
The shared payload model introduces no additional history or string store.

## Accounting and Ownership

A source UUID distinguishes a context incarnation from another execution with
the same PID. Each component registration has its own instance and generation.
Recreating a component starts a new component lifetime.

The service maintains context lifetime totals, component-instance lifetime
totals, and one current `since_refresh` summary per component. A successful
`ComponentOwner::refresh` resets only the current summary and updates its
configuration attribution. Lifetime code counters and rolling outcome windows
continue; no historical refresh-summary store accumulates.

Every accepted observation updates lifetime and current-summary totals when it
is recorded. Work captured before a refresh can retain its original attribution
on retained events while counting in the current summary.

Event eviction preserves numeric totals. Closing a component retains its row
until bounded reclamation requires space. Reclaiming that closed row removes
its component aggregates; context lifetime totals remain available. Closing the
registration does not prove that its process exited.

The embedding application or deployment owner decides health, readiness,
alerts, and recovery. Relay records observations, outcomes, timing, and coverage;
it has no active/recovered conditions or error-code closure operation.

## Resource and Wire Boundaries

An enabled context reserves its backing storage at startup. Component/code
reservations, circular event headers, reclaimable detail blocks, outcome buckets,
query workspaces, and projection workspaces have independently enforced limits.
Recent events share one circular history across components; new evidence can
evict older evidence while reserved summary counters continue updating.
History uses a runtime-sized `circular-buffer` allocation with resizing hidden.
Startup admission includes its header, alignment, and event slots. Allocation
failure for this history invokes the global allocation-error handler; fallible
pool reservations return `DiagnosticError::Allocation`.

`DiagnosticLimits.max_owned_bytes` bounds the admitted context backing, not total
process RSS. It excludes allocator overhead, caller-owned inputs and decoded
snapshots, producer handles, callback captures, and operational output storage.
File-sink queues and on-disk retention remain governed by logging configuration.

### Query Budgets

Query pages have independent startup capacities. `max_counters` and
`max_window_buckets` reserve recording state across the source;
`max_query_counters` and `max_query_window_buckets` bound copied rows in each
query workspace. Smaller pages do not reduce recording or retention capacity.

| Setting | Default | Scope |
| --- | --- | --- |
| `max_queries` | 4 | Simultaneously leased query workspaces. |
| `max_query_components`, `max_query_events` | 64, 256 | Component and event rows per page. |
| `max_query_counters`, `max_query_window_buckets` | 256, 512 | Matched code counters and outcome buckets per page. |
| `query_text_bytes` | 64 KiB | Copied text per workspace. |
| `max_snapshot_bytes` | 128 KiB | Encoded JSON response per workspace. |

Larger selections continue through `DiagnosticSnapshot.continuation`. Each
component row is atomic: its matched counters and covered window buckets must
fit together in a page, along with its text and encoded response. If a single
selected component cannot fit, reading returns `DiagnosticError::SnapshotCapacity`.
Increase the relevant page budgets or narrow the selection. This error does not
change retained evidence or accepted totals. Event-only queries can set
`max_components` to zero.

For recording and projections without snapshot reads, set `max_queries` to zero
at startup. The enabled context then allocates no query pool or page backing;
unused query capacities are ignored. Snapshot calls return
`DiagnosticError::QueryDisabled`, while recording, retained history, and
projections remain enabled. This is distinct from disabling the entire service.
Enabled query paths remain preallocated and enforce their own capacities.

### Memory Inspection

`Diagnostics::memory_usage()` and `DiagnosticsReader::memory_usage()` return the
same `DiagnosticMemoryUsage` view. The history and detail-pool fields distinguish
reserved backing, occupied capacity, and logical text:

| Fields | Meaning |
| --- | --- |
| `event_slot_bytes`, `event_capacity` | Compiled size of one private retained event header and the admitted number of history slots. |
| `history_reserved_bytes` | Complete circular-buffer allocation, including shared header, alignment, and all event slots. |
| `history_occupied_bytes` | Retained event count multiplied by `event_slot_bytes`; excludes the shared buffer header and unused slots. |
| `detail_capacity_bytes`, `detail_metadata_bytes`, `detail_reserved_bytes` | Whole-block payload capacity, metadata reserved for every block, and their combined backing bytes. |
| `detail_bytes` | Existing gauge for occupied payload blocks, including unused space within those blocks. |
| `detail_logical_bytes`, `detail_slack_bytes` | Retained UTF-8 message/correlation bytes and unused payload space within occupied blocks. |

`detail_reserved_bytes` equals `detail_capacity_bytes + detail_metadata_bytes`.
`detail_bytes` equals `detail_logical_bytes + detail_slack_bytes`. Free payload
capacity is `detail_capacity_bytes - detail_bytes`. Block metadata differs from
the existing `metadata_bytes` gauge, which describes admitted registration text.
A pool rounds payload capacity down to whole blocks; block size comes from
`DiagnosticLimits.detail_block_bytes` and defaults to 256 bytes.

Each retained event packs its message, session ID, and request ID into one
block chain. Compact ranges preserve the three fields, including present but
empty strings; UTF-8 characters are never split across blocks. Fields are
admitted in message, session, then request order. A field that cannot fit in the
whole pool is omitted without evicting prior evidence; selected fields can
reclaim older events when free blocks are exhausted. Projections still receive
the independently bounded input fields.

Inspection derives the breakdown from existing storage. Logical text bytes
require a bounded scan of block metadata when the view is requested; recording
adds no size ledger, per-event size field, or additional retained store. Disabled
contexts report zero for every gauge. Eviction reduces occupancy and returns
blocks for reuse while the reserved backing remains allocated. These values do
not measure resident pages or whole-process working-set memory.

This remains a separate Rust inspection API; the canonical diagnostic snapshot
and runtime endpoints do not acquire memory fields in phase one. Per-entry and
per-component attribution, process-memory correlation, and integration with the
existing resource-metrics surfaces are deferred to a later development phase.

Snapshot coverage reports rejected observations, truncated detail, eviction,
and saturated counts. A saturated count is a lower bound. Inspect coverage when
interpreting missing evidence. JSON encodes 64-bit counts and sequences as decimal
strings to preserve precision in every supported language.

Diagnostic detail and caller-supplied correlation can contain restricted data.
Byte limits do not redact payloads or credentials. Authorize access to readers
and their responses; keep correlation out of aggregate keys. The service does
not capture ordinary logs, prompts, or request bodies automatically.

## Operational Logging and Legacy Reports

Create the context before logging when startup failures need to be inspectable.
Pass it to `LoggingRuntime::configure_with_diagnostics` to reuse existing
filters, formatters, stderr, and file sinks. Eligible typed observations use an
optional logging projection; ordinary operational log lines do not automatically
enter diagnostic history.

Projection callbacks receive `DiagnosticOutputSummary`, which contains only
validated built-in classification, severity, outcome, occurrence count, sequence,
time, and a service-generated component UUID. It contains no detail, component
name, plugin context, configuration attribution, or caller correlation. Extension
observations remain readable but do not automatically produce output. This is a
Rust callback contract change from the initial foundation proposal.

Core builds the summary at recording, independently of retained evidence. It
enforces this boundary for ordinary recording calls as well as state-only calls.
There is no automatic replay from diagnostic readers to logs, legacy reports,
subscribers, or exporters. Existing event sanitization and export ordering remain
unchanged.

Recording is independent of log thresholds. Projections execute outside the
state lock, and sink failures use a state-only recording path to avoid recursive
delivery through a failing sink. Shutdown detaches projections before draining
sinks. Explicitly configured file sinks remain required, with existing queue,
rotation, and delivery behavior.

OpenTelemetry subscriber diagnostics and OTel-dependent plugin reports remain
legacy-only. They are not projections of this canonical store. Their integration,
report deduplication, and reader migration are deferred to a separate phase.

## Implementation Scope

This phase provides Rust contracts, bounded recording/state/queries, logging,
configuration-inheritance notices, and selected plugin activation observations.
The shared `DiagnosticClassifier<E>`
interface returns `Classification` values without recording or changing source
errors. The production adapters are `PluginErrorClassifier` and
`LoggingErrorClassifier`.

`PluginError::InvalidConfig` combines configuration file-read failures and
validation failures without preserving their structured causes. Its classifier
therefore emits `plugin.configuration_invalid` with the `unknown` failure class.
It never infers a cause from error text. A producer with structured validation
evidence can explicitly author that code with `invalid_input`.

### Catalogue Families and Extension Points

`DiagnosticDomain` identifies the owning subsystem. `PluginDiagnosticFamily`
groups related plugin codes within that domain; `Common` covers shared plugin
operations across execution mechanisms. `PluginExecution` separately describes
the observed execution mechanism when a producer can establish it.

Domain and family come from the individual catalogue entry. Success, failure,
and notice describe the observation kind and do not determine its owner. Today,
the three success codes belong to Logging, and the inheritance notice belongs
to Plugin/Common. The selector methods match those entries explicitly so adding
a new success or notice requires an intentional domain and family mapping.

When integrating a producer that needs a new code, update its canonical name,
domain, optional plugin family, catalogue listing, and selector tests together.
A future plugin success must select Plugin ownership and its applicable family;
it does not inherit Logging ownership from its observation kind. Add those codes
with their production recording sites in the owning integration phase.

### Plugin Producer Boundaries

Phase one owns the shared diagnostics foundation and generic host configuration
and component activation boundaries in `core`. The phase 5 plugin workstream
owns mechanism-specific producer integrations in the native loader, worker
client/SDK, and `worker-proto` transport. Crate location alone does not determine
scope: `core` also contains deferred native and worker code.

| Surface | Current production coverage | Workstream |
| --- | --- | --- |
| Logging adapter and sinks | Typed recording and optional log projection | Phase one |
| Common component activation | Registration failures and activation unwinds, recorded once at the owning operation | Phase one |
| Shared host configuration | One canonical inheritance notice per contributing ambient file, preserving existing warnings/reports | Phase one |
| Native ABI and dynamic trust/policy | Existing execution/report behavior; no canonical mechanism-specific adapter | Phase five |
| Worker launch, handshake, RPC, remote observations, and protocol transport | Existing execution/report behavior; no canonical worker integration | Phase five |

The activation adapter supplies the canonical `activation` phase through
`PluginPhase::Activation` and leaves `PluginObservationContext.execution` unset.
It does not automatically observe validation, runtime, or policy stages.
`PluginExecution::{NativeAbi, WorkerProtocol}` and the other `PluginPhase`
values are typed construction helpers for producers integrated later. Their
round-trip tests establish representation support; production coverage comes
from recording at an integrated operation boundary.

`PluginObservationContext` uses distinct `PluginExecutionName` and
`PluginPhaseName` wrappers for optional execution and phase
names. Future strings retain their original names on snapshot decoding and
reserialization. Missing or null fields remain absent, and non-string values
are rejected. Core admits recognized context into a private compact
representation before recording; unfamiliar decoded context can still be read
and forwarded without becoming accepted local input or a counter key.

Known context construction and approved summary classification use borrowed names without
string allocation. Owned snapshot decoding allocates caller-owned values;
transport adapters must enforce their metadata and payload limits before
materialization. The schema permits future names within a supported snapshot
envelope; unsupported envelope versions still require negotiation.

The phase-one built-in catalogue contains logging failures/successes, six common
plugin failures, and `ConfigurationInherited`. The inheritance notice records once per
contributing ambient file at configuration resolution, using a separate
`plugin.configuration` recorder in the host's selected context. The explicitly
supplied file is excluded from inheritance notices. This state-only producer
retains generic safe detail; paths remain in the established operational warning
and configuration report. Reading or copying that report never records again.
Disabled collection or exhausted diagnostic capacity does not change configuration
results. Standalone validation and discovery use the same resolution helpers
without canonical recording or process-default initialization.

`ComponentReenabled` is deferred from the canonical catalogue until a production
producer is integrated. Its existing test-only helper and legacy report strings
remain unchanged; there is no production emitter today.
Runtime/upstream, binding, native-status, dynamic trust/policy, and worker
classifiers and their unused code families arrive with their owning producer
integrations. OTel failures, export successes, and context-expiration
observations arrive with the separately scheduled OTel integration.

CLI composition and authorized HTTP inspection are implemented in phase 2,
as described below. Daemon workers and broker collection follow in phase 3; public language-binding APIs in phase 4; dynamic-plugin
transport in phase 5; and API conformance in phase 6. Detailed memory attribution
and resource-metrics integration follow in phase 7. That phase will also evaluate
read-only typed views over leased, copied query workspaces to avoid a JSON
round-trip for Rust readers. Phase 1 retains canonical JSON access and explicit
owned snapshot conversion; consuming a page never pins retained history.
CPU collection and generic measurement types/schema are also deferred; existing
lifetime/timing fields remain available. Restart persistence remains later work.
The core API starts no diagnostics listener or background collection service.
CLI inspection reuses the existing gateway listener.


## CLI Startup and Inspection

Diagnostics is compiled in and disabled by default. Configure it through the
existing CLI configuration layers:

```toml
[diagnostics]
enabled = true
http_read = true

[diagnostics.limits]
max_events = 256
max_queries = 4
max_snapshot_bytes = 131072
```

An explicit configuration replaces the user layer; the system layer retains its
existing precedence. `run --config` takes precedence over the inherited path.
`NEMO_RELAY_DIAGNOSTICS` and `NEMO_RELAY_DIAGNOSTICS_HTTP`, then
`--diagnostics=true|false` and `--diagnostics-http=true|false`, override their
respective settings. Limits come from the merged configuration. Command-line
settings apply to that CLI process; an MCP client does not override an already
running gateway's settings. A named logging
configuration file affects logging only. Startup selects and validates diagnostics
before configuring logging or activating plugins, and reuses the parsed inputs
for runtime configuration. Repair/inspection commands keep their existing
no-ambient configuration policy; daemon composition remains a later integration.

For an explicit local view after command completion and logging teardown, use
`--diagnostics-final`. It writes one bounded canonical JSON page to stderr and
does not change command stdout or exit codes. Restricted detail appears only
because the caller requested inspection. Pre-context failures cannot be retained.

### Existing Gateway Reads

```bash
nemo-relay diagnostics --capabilities
nemo-relay diagnostics --gateway-url http://127.0.0.1:4040
nemo-relay diagnostics --query '{"component_key":"cli.gateway","max_events":10}'
```

Inspection connects only to an existing local gateway over the existing pinned
TLS tunnel. It loads existing private credentials and sends a domain-separated
diagnostics-read capability. Provider, hook, and shutdown credentials do not grant
read access. Plain HTTP returns `426 authenticated_transport_required`; the
diagnostic TLS connection has a five-second delivery deadline and exposes only
diagnostic routes. Reads require whole-context authority because pages include global
totals. Browser-origin requests are rejected. Enable HTTP inspection explicitly
with `http_read`; loopback or public health access alone grants no authority.

Inspection does not acquire, start, recover, or health-poll a gateway, and does not
refresh its idle timer. A reused gateway keeps its own immutable diagnostic
settings. Diagnostic settings are excluded from execution fingerprints, including
forwarded diagnostic environment variables. Inspect effective settings with
`--capabilities`; change them through the existing explicit gateway restart
workflow. An older or unexposed endpoint reports unsupported/unavailable.

| GET route | Response |
| --- | --- |
| `/_nemo_relay/v1/diagnostics/capabilities` | Effective enablement, limits, producer coverage, and query availability; no snapshot lease required. |
| `/_nemo_relay/v1/diagnostics` | One canonical snapshot page. |
| `/_nemo_relay/v1/diagnostics/components` | Canonical page with recent-event rows disabled. |
| `/_nemo_relay/v1/diagnostics/events` | Canonical page with component rows disabled. |

The optional `query` parameter contains percent-encoded JSON. Supported fields
mirror `DiagnosticQuery` and add `schema_version`. Counts, sequences, and cursor
values retain canonical decimal-string encoding. Unknown fields, oversized
selectors, requests above configured page limits, and query strings above 4 KiB
are rejected. Continuations retain the same selection and require authorization
on every request; changed source state or scope returns `409 invalid_cursor`.

All diagnostic responses use `Cache-Control: no-store`. Errors contain stable
reasons without raw query/configuration values: `disabled` or `query_disabled`
(`503`), `unsupported_schema` (`406`), invalid queries (`400`), invalid cursors
(`409`), missing/invalid credentials (`401`/`403`), busy response/query capacity
(`429`), and snapshot capacity (`422`). Diagnostic unavailability does not affect
gateway execution admission.

### CLI Producer Ownership and Memory

The process owns finite recorders for command completion, post-startup
configuration attempts, gateway bind/serve/shutdown, acquisition/recovery,
child spawn/wait/cleanup, hook delivery, and upstream transport/body stages.
Each boundary records its own outcome once. Command and child/request outcomes
are distinct scopes, so their sum is not a unique failed-request count.
Nonzero child exit is a notice; provider HTTP status is not inferred to be a
transport failure. Header receipt and body completion are separate observations;
a cancelled stream does not fabricate completion. Flattened errors retain an
`unknown` cause. Logging and plugin adapters keep their existing recording owners.

HTTP response storage is separate from core retention/query pools. It reserves
`max(1, max_queries)` slots of `max(8192, max_snapshot_bytes)` bytes, using checked
startup admission. Defaults add four 128 KiB response slots, or 512 KiB of payload
backing. A response owns its slot until the final body reference is dropped;
core snapshot leases are released before network delivery. Diagnostic TLS
connections have separate permits with the same concurrency, a 16 KiB HTTP
input buffer, a 32 KiB TLS output limit, and a five-second connection deadline.
Existing gateway shutdown cancels those connections and stops new reads.
Discovery remains
available when collection is enabled with `max_queries = 0`. Requests do not
alter counters, refresh markers, or deployment-owned health policy.

Native/worker plugin callbacks, daemon collection, language bindings, OTel
migration, and detailed resource attribution remain assigned to later phases.
Configured log files retain their existing required-sink behavior.
